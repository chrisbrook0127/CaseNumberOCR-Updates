# MFCase project rules
Maintain standalone MFCase; preserve the approved application architecture, recognition and local learning, existing review and file operations, and its own updater. See APP_BASELINE.md and existing PROJECT_STATUS.md and PUBLISH_SCOPE.md; the latter two are historical records and do not establish the current approved version.

For existing 2008 workflow, retain its approved literal 08- validation, crop rules, recognition paths and precedence of verified corrections/anchors. Confirm exact thresholds, crop geometry, review eligibility, normalization, renaming and sending from the approved source and current explicit decisions; do not transplant earlier rules from a historical release. Preserve approved manual corrections, separate prefill/candidate from verification, and protect data and original files. Do not change models, thresholds, eligibility, location policy, review or file movement without explicit authorization. Maintain responsive PAUSE/STOP and nonblocking review when required by the approved workflow. Benchmark real workloads against baseline; no accuracy sacrifice for speed.

Keep processing and learning local; no case PDFs, images, learning examples, model weights, user state, credentials or private logs in the public repository, release packages or CI. Use synthetic test fixtures only. Keep software update and learning update flows distinct where approved; preserve settings, learning and files during updates. Stable and test release channels remain distinct. No publishing, updater-channel changes or stable promotion as part of infrastructure work.

Before release: verify actual code, tests, Windows behavior, archive integrity and rollback, exact source/asset identity, correct update feed and authorized release class; verify remote release and updater independently. Project Sources is a separate delivery check requiring the correct authorized project and actual attachment read-back. Never claim it from a GitHub upload alone.
